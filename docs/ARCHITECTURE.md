# Architecture (final)

```
 web page (tab)                 extension                                   local backend (Node, holds the key)
 ──────────────                 ─────────                                   ───────────────────────────────────
 content script ──bf:convert──> service worker ──HTTP JSON──> handler ─> engine ─> provider ─> Ollama (local) or Gemini (free key)
  scan, classify, regions        translation-service           validate  prompt      ollama | openai-compat
  scheduler (viewport-first,     cache (IndexedDB), dedupe,    limits    retries    (anthropic, mock)
  parallel, pause/stop)          in-flight sharing,            rate      repair
  inline markup, replacer        quota breaker (chrome.storage) log      validate
 popup ──tabs/runtime messages──────────────┘
```
The page never talks to the network and never sees the backend URL. The extension contains no credentials. The API key is read from `.env` by the backend only.

## Content script (`extension/src/content`), injected only when you click Translate
1. **scanner.js** walks the DOM (pruning protected and advertisement subtrees) and builds *runs* per host element.
2. **inline.js** turns a run into a template string: `⟦1⟧…⟦/1⟧` for inline wrappers (links, bold…), `⟦2=code⟧` for protected inline elements. Only the **kind** (`code`, `img`, `br`, `ui`, `hi`, `x`) of a protected element is ever sent.
3. **classifier.js, ads.js, region.js** decide what is main-content prose: strong ad signals prune a subtree, containers are scored by prose volume, density and link density, then tightened to the smallest container holding 65% of the prose; furniture (share bars, newsletters, sidebars, cards) is discounted; dictionary entries are found structurally.
4. **controller.js** is the scheduler. After one synchronous scan it:
   - **dedupes** identical blocks (same template, role, heading) into groups: one request, many applications;
   - **prioritises** groups by real layout: on screen (top first) → up to 1.5 screens below → further below → above (nearest first), and re-sorts what is left when you scroll more than half a screen;
   - **packs** each request off the front of that queue (`batching.js`: up to 12 blocks / 1,800 characters, a long paragraph alone, never over 3,900 characters per block);
   - runs **at most N requests in flight** (default 2, clamped 1-4), starting the first one immediately after the scan;
   - applies each answer when it arrives, after validating placeholders; a short or malformed reply fails only the affected blocks (`missing-result`, `bad-response`, `placeholder-mismatch`), never hangs the run;
   - halts scheduling on a quota error or backend failure (in-flight answers still land, nothing new is sent);
   - supports `pause()` / `resume()` / `stop()` (keep what is done) / `restore()` (cancel, discard late answers, put the DOM back exactly);
   - shares one queue with **dynamic content** (opt-in observer), so a block is never queued or translated twice.
   - **cache first**: before any model request the scheduler asks the worker for saved translations (`bf:lookup`: cache only, never the backend). The highest-priority 64 blocks are looked up first and painted at once; the rest are looked up in the background while the first request already runs, and a block whose lookup is pending is never sent to the model. Hits leave the queue, so a saved block can never wait inside a batch for a slow neighbour; a saved answer that no longer fits the block's markup is ignored and the model is asked instead;
   - **timings** (`getStatus().perf`): ms from the Translate click to the first block painted (any / from cache / from the model), cache lookup time, requests, request and per-block average and p95, cache hit rate;
   - **progressive, viewport-first**: the first request holds only the blocks on screen, and each answer is validated and applied the moment it returns (no waiting for the page). After the visible blocks come the ones within 1.5 screens below, then the rest, then the content above. A `scroll` listener (passive, debounced 50 ms; removed on Restore) re-ranks everything still waiting, so blocks the reader has just scrolled to jump ahead of distant ones even while a request is in flight (no IntersectionObserver is needed: the scheduler ranks real layout rects);
   - **sentence groups**: the block is the unit. Only a block longer than the request's `maxItemChars` is cut, and only at sentence ends outside every link/bold span (`sentence-groups.js`), so each group is a valid template and neighbouring sentences stay together. Groups are ordinary scheduler groups (deduped, cached, prioritised); the answers are joined in order and applied as ONE block, so a half-translated paragraph never appears; if a group fails the block stays English and its unsent groups are cancelled;
   - **hints from the backend** (`GET /health` -> service worker `bf:hints` -> content script): `maxConcurrency` and `batch {maxItems,maxChars,maxItemChars}`. They can only lower the setting/limits. Ollama advertises 1 request at a time and 6 blocks / 500 chars; other providers advertise nothing, so their behaviour is unchanged;
   - **progress**: status carries `pendingVisible`, `pendingBackground` and `phase` (`visible` | `background` | `idle`) next to `converted`, `pending`, `failed`; the popup shows "visible content first" then "rest in the background";
5. **replacer.js** applies a validated answer by *reusing* the original inline elements (listeners and attributes survive) and keeping the original nodes for restore. Nothing is added to the page.

## Service worker (`extension/src/background`)
- **translation-service.js** answers `bf:convert` and never throws or leaves a message unanswered. Per request: key each block (SHA-256 of schema, **prompt version, model, page title, role, heading, template**; version and model come from the backend's free `/health`), collapse duplicates, claim keys synchronously in an in-flight map (concurrent identical requests share one backend call; keys are always released), read the cache, send **one** backend request for the true misses, validate, cache, share.
- **translation-cache.js + idb-storage.js**: IndexedDB store (`entries`, indexed by `lastUsedAt`). 5,000 entries / ~5 MB / 90-day TTL; LRU eviction to 80%; hourly `lastUsedAt` refresh; reads re-validate placeholders; corrupt entries are deleted and counted as misses; records whose timestamp is missing or non-numeric are swept before anything is evicted; storage errors pause the cache for 60 s while translation continues; disk-full frees half and retries once; memory storage is the fallback when IndexedDB is unavailable. Only a hash key and our Hinglish output are stored.
- **Quota circuit-breaker**: after a daily-quota error, misses are answered locally until the provider's reset time (max 24 h). Stored **per model** in `chrome.storage.local` (`quotaBreakers`), reloaded when the worker restarts, expired entries dropped on load, malformed data ignored. Cache hits are never blocked.
- **backend-client.js**: one POST with an anonymous install id; 45 s timeout; one retry for a network failure only; structured errors (including `retryAfterSec`).

## Backend (`backend/src`)
`server.js` (node:http), `handler.js` (routing, optional `x-bf-token`, rate limit, validation, error mapping), `engine.js` (chunking, parallel chunks, bounded retries with backoff, one repair pass, per-item errors), `validate.js` (placeholders, no Devanagari, numbers, acronyms, URLs, plausible length, not-unchanged), `prompts/` (immutable `v1.js`, default `v2.js`), `providers/` (`ollama`, `openai-compat`, `anthropic`, `mock`, typed errors).

**Claude** (`providers/anthropic.js`, default): `POST https://api.anthropic.com/v1/messages`, key from `ANTHROPIC_API_KEY` only (never `LLM_API_KEY`), in the `x-api-key` header only. Claude 5 ids (`claude-haiku-5-5`, ...) get `thinking: {type: "disabled"}`, `output_config.effort: "low"`, no `temperature` (a non-default one is a 400) and a cacheable system block; other ids keep the plain request. Errors: 401/403 `auth`, 429 `rate-limit` (retried), 5xx/529 `unavailable` (retried), `truncated`, `refused`, and three request-level failures worded by us with no provider text: `no-credit`, `model-not-found`, `invalid-settings`. **Selected text** (role `selection`, set by the extension) is sent with `prompts/v2-selection.js`, a compact hinglish-v2 with the same rules and JSON contract; the role also keeps those cache entries apart from page text. Validation additionally allows a short word or phrase to change length freely and a leading "Sure"/"Here is" when the source starts that way.

**Languages** (`extension/src/shared/languages.js`): `hinglish` (default) and `tanglish`, remembered as the `targetLanguage` setting. Every request carries `lang`; the backend validates it (unknown = 400) and `getPromptForLanguage` picks the prompt: Hinglish keeps its versioned prompts untouched (full v2, compact selection variant), Tanglish uses `prompts/tanglish-v1.js` for page text and selections. The JSON field stays `hinglish` for both so the engine, parser and DOM code are shared. Validation rejects Devanagari AND Tamil script in either mode, and allows Tanglish a longer length ratio (romanised Tamil is spelled out). **Cache keys** hash `[schema, lang, promptVersion, model, title, role, heading, text]`; Tanglish uses its own prompt version (`tanglish-v1`), Hinglish the backend's; an answer is cached only when the backend reports the prompt version expected for that language. Whole-page runs fix the language at start; translating again in the other language restores the original first. The selection panel's choice is saved by the service worker (`bf:set-language`), never by the page script.

**Provider selection** is one switch: `PROVIDER` in `.env` -> `providers/index.js` builds exactly one adapter; the engine has no fallback chain, so choosing `ollama` can never route text to a cloud API. **Ollama adapter** (`providers/ollama.js`): `POST {OLLAMA_BASE_URL}/api/chat`, `stream:false`, `think:false` (Qwen3 reasoning off; `<think>` blocks are also stripped if an older server ignores it; a model that rejects the field is retried without it), `format` = JSON schema for `{results:[{id,hinglish}]}` (plain JSON mode let qwen3:4b echo the request instead of answering), `options.num_ctx` 8192 and `num_predict`. No key, no Authorization header; config drops cloud keys and `BASE_URL` for this provider; a non-loopback host is refused unless `OLLAMA_ALLOW_REMOTE=true`. Errors: connection refused -> `ollama-not-running` (503, not retried), 404 -> `ollama-model-missing` (503, names `ollama pull`), abort -> `timeout` (504), unreadable/mis-shaped reply -> `bad-json` (retried per `RETRIES`, then 502), `done_reason=length` -> `truncated`, blank -> `empty-response`. The Ollama messages are written by the adapter; no model text is echoed. Defaults for Ollama: `REQUEST_TIMEOUT_MS=40000`, `RETRIES=0`.
Local-model protection: Ollama gets a tight output budget (`40 + 25 x items + 0.9 x source chars` tokens, about twice a normal answer) because one repetition loop ("bhi bhi bhi...") at ~5 tokens/s otherwise holds the only inference slot for minutes; hitting it is retried once (it is random), timeouts are not retried, `RETRIES` defaults to 1.
Health hints: `/health` also returns `maxConcurrency` and `batch` when configured (`MAX_CONCURRENCY`, `FIRST_BATCH_ITEMS` = size of the very first request, Ollama 1, `BATCH_MAX_ITEMS`, `BATCH_MAX_CHARS`, `BATCH_MAX_ITEM_CHARS`; Ollama defaults 1 / 6 / 500 / 600).
Error handling: a daily-quota 429 (named per-day quota, `insufficient_quota`, or a provider wait over 60 s) is **never retried**; transient 429/5xx/timeouts are retried at most `RETRIES` times with exponential backoff, honouring a short provider hint and refusing waits over `MAX_RETRY_WAIT_MS`; truncated or empty model replies are explicit errors. Responses to the extension are 503 `provider-quota-exhausted` / `provider-rate-limit`, 502 `provider-auth`, 504 timeout, with messages written by us (no provider text, no key). Logs hold counts and timings only.

## Selection mode (`extension/src/selection`), the default
`selection.js` is the extension's only always-loaded script (manifest `content_scripts`, http/https top frames, `document_idle`). It adds listeners and nothing else until a valid selection exists.
- **selection-core.js**: reads the selection from a *cloned* range (page untouched), inserting line breaks at block boundaries and dropping protected nodes; refuses selections made in/at inputs, textareas, selects, contenteditable, role=textbox, password fields, CodeMirror/Monaco/Ace/ProseMirror/Quill editors, `pre`, and inside inline `code` only. `planSelection` turns it into blocks (one per line; lines without Latin letters pass through untouched; `⟦ ⟧` stripped so text cannot forge placeholder tokens; >2,000 chars refused; a block longer than the request limit becomes whole-sentence groups via `sentence-groups.js`). `translatePlan` does one cache-only `bf:lookup`, then sends only the misses through the normal `bf:convert` path (worker cache + dedupe, backend Hinglish-v2 prompt + validation) in batches (up to 3 requests at once for a hosted model so a long selection stays fast; 1 at a time when the backend advertises it, as Ollama does) using the backend's hints, with progress after each. Selections send no page title, heading or URL, so saved translations are shared across pages.
- **panel.js**: a closed shadow root on `<html>` (not `<body>`), `position: fixed` (no layout effect), text only via `textContent`, real buttons with labels, `role="dialog"`, `aria-live` result, focus moves in and returns on close, light/dark and reduced-motion aware.
- **selection-app.js**: the controller. The button appears after mouse-up / key-up / selection change (debounced) and is repositioned on scroll; **only a click (or Alt+Shift+T) starts work**. One run at a time (a newer selection or Close supersedes: late answers are discarded; repeated clicks on the same selection do not send a second request). Escape closes the panel (and only then swallows the key). Setting `selectionMode` (default true) and the master switch are read on each selection.
- Errors map to plain messages (`friendlyError`): Ollama not running / model missing (backend wording naming the fix), backend not running, timeout, unusable model output, quota.

## Popup (`extension/src/popup`)
Reads settings from `chrome.storage.local`; injects the content script on click (`chrome.scripting.executeScript`, the only place it happens); sends `translate`/`pause`/`resume`/`stop`/`restore` to the tab and `cache-stats`/`clear-cache` to the worker; polls status every 250 ms while work is active **or still in flight**, so the numbers shown are final.

## Message protocol (`shared/messages.js`)
popup/content → worker: `bf:convert`, `bf:cache-stats`, `bf:clear-cache`. popup → content: `bf:translate`, `bf:pause`, `bf:resume`, `bf:stop`, `bf:restore`, `bf:status`, `bf:set-observe`, `bf:explain`. `shared/tokens.js` (token grammar and validation) is imported by both the extension and the backend so both enforce one contract.

## Privacy summary
In Selection mode only the text you selected and clicked Translate on is sent (to the local backend). With `PROVIDER=ollama` the backend only talks to the local Ollama server and the text below never leaves the machine. With Gemini, it is sent to the backend (then Google): prose of the blocks you translate (protected inline content as a kind label), role, nearest heading, page title (switchable). Never sent: URLs, ads, nav, sidebars, code, form fields, buttons, preserved headings, existing Hindi. Stored locally: hash key + Hinglish output only.
